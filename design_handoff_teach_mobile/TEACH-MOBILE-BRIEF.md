# Teach Mobile: метод и техническая база

Выгрузка знаний для продолжения работы в Claude Design.
Дата: 2026-09-03. Автор материала: Claude, по итогам разбора скилла `teach`.

Область: мобильное приложение-репетитор по любой теме, не только по языкам.
Аудитория: сам Олег и команда UZ.U1.D4, монетизация вне рассмотрения.

---

## 1. Откуда растёт идея

Основа: скилл `teach` Мэтта Покока из репозитория `mattpocock/skills`, лицензия MIT.
Это не код и не библиотека, это метод, записанный в виде инструкции для агента. Ценность
там в педагогике, а не в реализации, поэтому переносить нужно принципы, а не файловую
структуру.

Что уже проверено на практике в этой сессии:

- В Claude Code скилл работает как `/teach` и строит рабочее пространство из файлов:
  миссия, ресурсы, записи об усвоенном, уроки в HTML, переиспользуемые компоненты
- В ChatGPT метод пришлось переложить на Projects, потому что файловой системы нет.
  Состояние живёт в загруженных файлах, обновляется вручную через canvas
- Из этого следует главный вывод для мобильного: метод не требует файлов, ему нужно
  постоянное состояние и возможность его читать перед каждым решением. Файлы были просто
  доступным носителем

## 2. Метод, разобранный на принципы

Ниже каждый принцип и то, что он означает для интерфейса. Это основной материал для
проектирования.

### 2.1 Миссия как якорь

Обучение начинается не с темы, а с причины. Пока непонятно, зачем человеку предмет, любой
урок будет абстрактным, и нечем будет мерить, что учить дальше. Миссия меняется по мере
роста, и это нормально, но менять её нужно осознанно и фиксировать факт изменения.

Для продукта: миссия это не поле в онбординге, которое заполнили и забыли. Это живой
объект, к которому приложение возвращается. Каждый урок должен уметь ответить на вопрос
«зачем он мне», ссылкой на конкретный пункт миссии.

### 2.2 Знания берутся из источников, а не из памяти модели

Модель не является источником истины. Сначала находятся качественные материалы, потом на
них строятся объяснения, и каждое утверждение подкреплено ссылкой.

Для продукта: у урока есть библиография, она видна, а не спрятана. Отдельный экран
источников с оценкой доверия. Первая сессия по новой теме это не урок, а сбор источников.

### 2.3 Беглость это не то же самое, что запоминание

Умение вспомнить прямо сейчас создаёт иллюзию владения. Долговременное удержание строится
на трудностях: припоминание по памяти, интервалы между повторами, перемешивание близких
тем.

Для продукта: самый важный и самый неприятный принцип. Гладкая сессия, где всё получилось,
это плохой сигнал. Интерфейс не должен поощрять лёгкость. Метрика прогресса строится на
отложенных повторах, а не на пройденных уроках.

### 2.4 Зона ближайшего развития

Каждый урок должен быть на границе возможного: чуть выше текущего уровня, но достижимо.
Граница вычисляется из записей об усвоенном, а не из самооценки.

Для продукта: приложение само предлагает следующий шаг и объясняет, почему именно его. У
пользователя есть право переопределить выбор, но по умолчанию решает система.

### 2.5 Урок это одна победа

Рабочая память маленькая. Урок короткий, завершается быстро, даёт один осязаемый
результат, на который можно опереться дальше.

Для продукта: жёсткий бюджет. Один урок это одна цель и один цикл практики. Если материал
не влезает, это два урока, а не один длинный.

### 2.6 Знание делается лёгким, навык делается трудным

При передаче знаний сложность это враг, она съедает рабочую память. При отработке навыка
сложность это инструмент, усилие и есть механизм запоминания.

Для продукта: две принципиально разные части интерфейса. Объяснение мягкое, читаемое,
с примерами. Практика жёсткая, без подсказок в поле зрения, с ответом только после
попытки.

### 2.7 Петля обратной связи должна быть тесной

Отклик на действие приходит немедленно и по возможности автоматически.

Для продукта: это то, ради чего вообще нужен мобильный клиент, а не документ. Проверка
ответа на месте, без ожидания генерации, там где это возможно.

### 2.8 Справочники живут дольше уроков

Урок проходят один раз, справочник открывают годами. Шпаргалка, набор формул, список поз,
таблица синтаксиса, глоссарий. Это сжатая суть, отдельный тип объекта.

Для продукта: библиотека справочников это второй по важности раздел после сессии. Их
хочется листать, искать по ним и держать офлайн.

### 2.9 Глоссарий как общий словарь

Как только термин определён, он используется одинаково везде. Без этого объяснения
начинают противоречить друг другу.

Для продукта: единый список терминов на тему, термины в тексте кликабельны и раскрываются
поверх, без ухода с экрана.

### 2.10 Мудрость приходит от людей

Настоящая проверка навыка происходит вне учебной среды. Тьютор отвечает, но по вопросам,
требующим опыта, отправляет к сообществу: форум, локальная группа, живой класс.

Для продукта: раздел с сообществами по теме. Честно ограниченная роль приложения, оно не
претендует на замену практики.

### 2.11 Записи об усвоенном определяют следующий шаг

Фиксируется не то, что прошли, а то, что оказалось неочевидным: что человек сделал не так,
как правильно, почему это важно. Эти записи и есть память системы.

Для продукта: центральная сущность. Из неё считается зона ближайшего развития, из неё
строится очередь повторов, по ней видно прогресс.

### 2.12 Предпочтения фиксируются

Как человек хочет, чтобы его учили, накапливается отдельно и учитывается при планировании.

Для продукта: настройки не в виде галочек, а в виде накопленных наблюдений, которые можно
подтвердить или отменить.

## 3. Что плохо переносится на мобильный и требует решения

- Уроки в оригинале это HTML-файлы, которые открываются в браузере и красиво печатаются.
  На телефоне нужен либо нативный рендер набора блоков, либо вебвью с контролируемым
  набором компонентов. Второе быстрее, первое приятнее в использовании
- Переиспользуемые компоненты в оригинале это файлы в папке. В приложении это библиотека
  типов блоков в коде, а модель выбирает из фиксированного набора, а не изобретает разметку
- Команда «открой файл» отсутствует как понятие
- Длинный текст не работает на телефоне вообще. Урок придётся резать на шаги с одним
  экраном на шаг
- Голос в оригинале отсутствует, а на мобильном это сильнейшая сторона. Для языков он
  критичен, для остальных тем полезен как способ припоминания вслух
- Офлайн: в оригинале не рассматривается, на телефоне обязателен хотя бы для повторов и
  справочников

## 4. Решения, которые нужно принять до проектирования экранов

1. Генерация урока: заранее и в фоне, или в момент открытия. От этого зависит, есть ли в
   интерфейсе состояние ожидания и насколько оно заметно
2. Кто владеет очередью повторов: алгоритм интервалов или модель. Смешивать опасно
3. Свобода модели в разметке урока: фиксированный набор блоков или произвольный HTML
4. Роль голоса: отдельный режим или сквозной способ ввода везде
5. Что происходит без сети: только повторы и справочники, или ещё и заранее скачанные уроки
6. Один предмет на пользователя или несколько параллельно. Это меняет всю навигацию

## 5. Техническая часть

### 5.1 Форма системы

Три слоя, границы между ними жёсткие.

- Клиент. Только представление, ввод, локальное хранилище и очередь синхронизации. Никаких
  ключей от моделей, никакой логики планирования обучения
- Оркестратор на сервере. Владеет состоянием обучения, собирает контекст, зовёт модель,
  валидирует ответ, считает интервалы повторов, ведёт кэш и версии промптов
- Провайдер модели. Заменяемый. Ни одна часть системы не должна зависеть от конкретного
  вендора

Причины держать логику на сервере, а не в клиенте: ключи, стоимость запросов, возможность
чинить промпты без релиза в сторах, единый кэш уроков между пользователями с похожими
миссиями.

### 5.2 Стек

С учётом .NET-фона имеет смысл: бэкенд на .NET 9, минимальные API, EF Core, Postgres в
проде и SQLite в разработке. Это же совпадает с тем, как построены DCC и трекер задач,
значит переиспользуются подходы и не растёт число технологий.

Клиент, три честных варианта:

- .NET MAUI. Один язык со всем остальным, но экосистема слабее, а качество анимаций и
  жестов ниже. Для интерфейса, где важна плавность, это заметно
- React Native с Expo. Лучшая скорость итерации, живая экосистема, простая работа со
  звуком и офлайном. Цена: второй язык и вторая сборка в проекте
- Нативно, по платформе за раз. Лучший результат и худшая скорость. Оправдано только если
  голосовая часть станет ядром продукта

Для инструмента на себя и команду разумен второй вариант, при этом бэкенд остаётся на .NET.

### 5.3 Модель данных, минимум

- `Subject` — предмет обучения, корень всего
- `Mission` — версионируется, старые версии не удаляются, смена фиксируется записью
- `Source` — материал с оценкой доверия и типом
- `Lesson` — цель, список блоков, ссылки на источники, ссылка на пункт миссии
- `LessonBlock` — типизированный блок: объяснение, пример, вопрос, задание, ссылка
- `LearningRecord` — что оказалось неочевидным, ошибка, исправление, причина важности
- `ReviewItem` — единица повтора со сроком, интервалом и историей ответов
- `Reference` — справочник, сжатая суть, переживает уроки
- `GlossaryTerm` — термин, определение, связь с уроками
- `Preference` — накопленное наблюдение о том, как человека учить
- `Session` — факт занятия, длительность, что делали, чем закончилось

Ключевая связь: `LearningRecord` порождает `ReviewItem` и влияет на выбор следующего
`Lesson`. Если эта связь не работает, продукт превращается в генератор карточек.

### 5.4 Генерация уроков

Не в момент открытия. Пользователь не должен смотреть на спиннер, пока модель пишет урок.

Схема: после каждой сессии оркестратор ставит фоновую задачу на подготовку следующего
урока, исходя из свежих записей об усвоенном. К моменту, когда человек вернётся, урок уже
лежит готовый и скачан на устройство.

Ответ модели не принимается на веру. Валидация по схеме: блоки только из разрешённого
набора, у каждого утверждения есть источник, длина в бюджете, вопросы имеют
однозначный ответ. Не прошло валидацию, значит повтор генерации, а не показ пользователю.

Промпты версионируются и хранятся отдельно от кода, чтобы правка педагогики не требовала
релиза.

### 5.5 Интервальные повторы

Брать готовый алгоритм, не изобретать. FSRS современнее и точнее, SM-2 проще и его хватает
для начала. Алгоритм детерминированный, на сервере, модель к расчёту сроков не
допускается. Модель формулирует вопрос, алгоритм решает, когда его задать.

### 5.6 Голосовой контур

Пайплайн: запись на устройстве, распознавание, ответ модели, синтез речи. Бюджет задержки
на полный цикл до полутора секунд, иначе разговор рассыпается.

Практическое замечание из разбора ChatGPT: распознанный текст показывает, что реально
услышано, а не что человек хотел сказать. Для языков это бесплатный детектор произношения,
и его стоит использовать явно, а не прятать.

Запись держать локально до конца сессии, отправлять только распознанный текст, если нет
необходимости в анализе самого звука.

### 5.7 Офлайн

Локальная база на устройстве, серверная считается главной. Синхронизация односторонняя по
конфликтам: сервер выигрывает, кроме ответов на повторы, которые всегда принимаются с
устройства с отметкой времени.

Офлайн обязательно работают: повторы, справочники, глоссарий, уже скачанные уроки. Не
работают: новые уроки, поиск источников, голосовой разбор.

### 5.8 Стоимость

Основные статьи: генерация уроков и голос. Уроки кэшируются и переиспользуются между
похожими миссиями, голос считается поминутно и растёт быстрее всего.

Что держит стоимость в рамках: генерация одного урока вперёд, а не пяти; короткие уроки;
кэш на уровне пары «цель урока плюс уровень»; голос только в режиме практики, а разбор
текстом.

### 5.9 Приватность

Записи об усвоенном это перечень того, чего человек не знает и в чём ошибается. Для
командного использования это чувствительные данные. Отсюда: обучение никогда не видно
руководителю, агрегаты по команде только обезличенные, экспорт и удаление своих данных
доступны пользователю.

### 5.10 Порядок работ

1. Ядро без модели: сущности, повторы по алгоритму, ручное заполнение урока. Проверяется,
   что метод работает на бумаге
2. Генерация уроков с валидацией, фоновая, с кэшем
3. Мобильный клиент с офлайном и повторами
4. Голосовой контур
5. Источники и сообщества

Первый пункт важнее, чем кажется. Если механика повторов и записей не даёт эффекта без
модели, добавление модели этого не исправит.

## 6. Что рисовать первым в Claude Design

По порядку ценности для проверки идеи:

1. Экран сессии: один шаг урока, без хлама, с честной сложностью в практической части
2. Экран разбора после сессии: ошибки, исправления, что уйдёт в повторы
3. Очередь повторов: главный экран возврата в приложение
4. Миссия: как она выглядит живой, а не заполненной один раз
5. Справочник: то, что открывают через полгода

Остальное вторично.
